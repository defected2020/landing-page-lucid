Outbound, built as a pipeline.

A small, trustworthy scraper feeds a database we own. Verified, scored, legally eligible contacts flow into a cold-email sequencer on secondary domains, and anyone who replies is nurtured in Mautic. The slow part is warming up inboxes, so that starts today.

Stop 3

Legal and deliverability ground rules

A German company processing personal data. GDPR applies to every record, wherever the person sits. These rules shape the data model.

Unsolicited B2B email, by market

MarketStatusWhat it takes
USA
CAN-SPAM		allowed, opt-outAccurate sender, honest subject, postal address in every email, opt-out honoured within 10 days.
UK
PECR, UK GDPR		allowed to corporate addressesSole traders and partnerships need consent. Identify yourself, offer opt-out, keep a legitimate-interest assessment on file.
Australia
Spam Act		inferred consentOnly addresses published on the business's own site, message relevant to their role, unsubscribe required.
Canada
CASL		conspicuous publicationSame as Australia. Keep the source URL of every address as proof.
Germany, Austria
UWG, DSGVO		no cold emailPrior express consent even for B2B. Use LinkedIn, phone, post, Google Business.
Rest of EUskip in v1NL, IT, FR are restrictive. Revisit later.

Two consequences for the scraper: provenance is a required field (source URL, source type, captured time on every email) and jurisdiction is a required field, because country decides eligibility before anything else.

GDPR housekeeping

  • Lawful basis: legitimate interest, Art. 6(1)(f). Write a one-page assessment and keep it with this plan.
  • Privacy notice link in every cold email; answer access and erasure requests within 30 days. Add a prospect-data paragraph to the site's privacy page.
  • Retention: delete or anonymise after 12 months without engagement. Every record carries its retention date.
  • One global do-not-contact list in Postgres, pushed to Mautic and the sequencer nightly. Unsubscribes, bounces, complaints, and "remove me" replies land there within 24 hours.
  • Never store special-category data, personal phone numbers, or anything from behind a login.

Platform terms

  • LinkedIn: never scraped. Sales Navigator by hand for DACH and enrichment, or a licensed provider.
  • Google Maps: the official Places API (New). Legal, free tier, no proxies. Scraping maps.google.com is fragile and against terms.
  • Company websites: crawl politely. Respect robots.txt, identify the bot with a contact URL, one request every few seconds per host, cache everything.
  • Directories: most forbid bulk scraping. Manual seed lists and APIs where they exist.

Mailbox providers

Google, Yahoo, and Microsoft all require aligned SPF and DKIM with DMARC, complaint rates under 0.3% (aim under 0.1%), valid reverse DNS, and one-click unsubscribe headers. The sequencer handles headers; we handle DNS.

Stop 5

The scraper

Simple, boring, and ours. Small stages that each read from and write to Postgres, so any one can be re-run without redoing the others.

StageDoesNotes
DiscoverA query like "dentist in Austin, TX" becomes company rows.Places API text search, paginated. Clutch, Wellfound, Crunchbase seed lists exported by hand.
CrawlCache home, contact, about, team, impressum, and a sitemap sample.Static fetch first. Playwright only when the page is a JS shell. Max about 8 pages per site.
ExtractStructured company and people fields from the cached pages.One Claude call per site with structured outputs enforcing the schema.
Find emailsCandidates with source type and URL.Explicit addresses, then mailto, then deobfuscated forms, then pattern guess from a known address, then an enrichment API for tier 1 only.
VerifyEmail status.Syntax, MX, disposable and role detection, then a verifier API for SMTP-level checks. Never probe SMTP from our own VPS; the IP is blacklisted within days.
AuditSite audit row.PageSpeed API for scores, own fingerprinting for CMS and features, headless screenshot for tier 1.
Classify and scoreSegment, scores, hook.Claude classifies and writes the hook; scoring is plain SQL and TypeScript so it stays explainable.
ExportCSV or API push.Only eligible, tier 1 or 2, not exported in the last 90 days.

Runtime and hosting

  • Node 22 and TypeScript. Claude Code can build and maintain it.
  • Crawlee for queues, retries, proxy rotation, and a Cheerio plus Playwright crawler pair.
  • Postgres 16 in Docker on the same box, Drizzle for the schema. Neon or Supabase if zero ops is preferred.
  • Cloudflare R2 or Hetzner Object Storage for raw HTML and screenshots.
  • Hetzner CX22 or CX32 in Germany, €4 to 8 a month. EU hosting keeps the GDPR story simple.
  • Cron per stage. No Kubernetes, no serverless. Nightly runs are enough.
  • A runs table and a daily summary by email or Telegram is all the observability v1 needs.

Claude in the pipeline

  • Used only where regex fails: extracting people and addresses, classifying the business, writing the hook.
  • Model claude-opus-5 with low effort for extraction and classification, default effort for tier 1 hooks.
  • Structured outputs enforce the schema; the pipeline never parses free text.
  • Frozen, cached system prompt; page text after it. Trim HTML to visible text first, which cuts cost five to ten times.
  • Nightly runs through the Batch API at half price. Roughly €10 a day for 500 extractions, €3 for classification, about €1 for 100 hooks.
  • Check the stop reason before reading content; log refusals and retry with cleaner text.

The meetup contact doing 30,000 a day is almost certainly hammering Maps or directories through residential proxies. That volume is not needed here, and its risk profile is worse than its return.

What makes it effective

  1. Quality gates before quantity. A lead counts only with a verified email, an eligible jurisdiction, and a segment.
  2. The audit is the product. Personalisation comes from measured facts about their site, not guesses.
  3. Provenance on every field. "Where did you get my email" is answered instantly.
  4. A feedback loop. Replies, bounces, and meetings flow back and tune the scoring weights monthly.
  5. Boring infrastructure. One VPS, one database, cron. It can be left alone for a week.

Stop 7

Email infrastructure and warm-up

The long pole. Domains need age and inboxes need history before they can carry cold volume. All of this starts before a line of scraper code exists.

Never send cold email from lucidcodelabs.com. It carries client mail, invoices, and the inbound SEO work.

Domains and inboxes

  • Three secondary domains now, for example lucidcodelabs.io, lucidcode.dev, lucidlabs.agency, getlucidcode.com. Prefer .com, .io, .co; avoid .xyz and .top.
  • Namecheap or Porkbun, WHOIS privacy on, a 301 redirect to www.lucidcodelabs.com so each domain resolves to a real site.
  • Two mailboxes per domain in month one, three at most. Human names: george@, g.beard@, plus one hello@ for replies.
  • Domain 1 on Google Workspace, domain 2 on Microsoft 365, domain 3 on Zoho. Mixed providers spread risk and cover both Gmail and Outlook placement.
  • Real display name, photo, and a signature with name, title, company, Berlin postal address, and website.

DNS per secondary domain

Verify with MXToolbox and mail-tester.com (aim for 10 of 10). Register every domain in Google Postmaster Tools and Microsoft SNDS.

Warm-up schedule, per inbox

Ramp 1Days 3 to 95 to 20warm-up emails a dayReply to real threads, subscribe to newsletters, use the inbox from a phone.
Ramp 2Days 10 to 1620 to 30warm-up, 40%+ repliesNo cold sends yet.
Ramp 3Days 17 to 235 to 10cold sends a dayTier 1 leads only, hooks reviewed by hand. Warm-up stays at 25 to 35.

Steady state: 3 domains, 2 inboxes each, 25 a day, so 150 cold emails a day and about 3,000 a month. Add a domain each month if metrics hold. Automated warm-up networks work, but Google has said they violate Workspace terms, so keep volumes conservative and pair them with real human activity. The first cold email goes out around day 21. That is the scraper's v1 deadline: 150 tier 1 and tier 2 leads ready by then.

Deliverability guardrails

  • Plain text, no images, no attachments, at most one link in the first email, preferably none.
  • Open tracking off. Pixels hurt placement and Apple Mail inflates opens anyway. Measure replies.
  • Tuesday to Thursday first, 08:00 to 11:00 in the prospect's time zone, 3 to 8 minutes between sends.
  • Bounce rate above 3% on an inbox: pause it three days and re-verify. Complaints above 0.1%: pause the whole domain a week.
  • Three to four subject lines and three bodies per step so no two inboxes send identical text.
  • Re-verify every email within 30 days of sending. Keep each inbox under 50 emails a day including warm-up.

The v1 sequence, segment B

  1. Day 0, 60 to 80 wordsName, one measured finding ("your site scores 31 of 100 on mobile and takes 6.4 seconds on a phone"), what it likely costs them in plain words, one question. Signature with postal address and a one-line opt-out.
  2. Day 3, same threadOne more finding or a screenshot link on the tracking domain. Two sentences.
  3. Day 7, different angleA relevant case study in one sentence. Ask whether someone else handles the website.
  4. Day 14, polite close"I will stop here; if it becomes relevant, reply any time."

Segment A uses the same rhythm with a capacity and white-label angle and no audit finding up front. Replies get an answer within four business hours; positives are promoted to Mautic with a booking link.

Stop 11

Scraper build brief

The seed for a separate, detailed planning session. A spec, not a plan; the plan produces milestones, migrations, and tickets.

Objective: turn "segment, market, city list" into 200 to 400 verified, scored, eligible contacts a day, with provenance on every field, running unattended on one VPS, with the first 150 tier 1 and 2 leads ready within 21 days.

In v1

  • Discover via Places API text search, one query template per segment B category.
  • Crawl up to 8 pages per site with Crawlee, Cheerio first, Playwright fallback.
  • Extract with Claude structured outputs; the deterministic email-finding chain.
  • Verify via one external verifier API.
  • Audit via PageSpeed plus CMS fingerprinting; no screenshots.
  • Score with SQL and TypeScript rules; Claude writes tier 1 hooks.
  • CSV export to the sequencer; suppression list export.
  • A runs table and a daily summary email.

Not in v1

  • Directory scraping, anything LinkedIn, residential proxies.
  • Screenshots, a UI, multi-worker queues.
  • Mautic API sync. CSV import is fine for the first month.

Done means

  • Fresh VPS to running pipeline in under an hour from the README.
  • A nightly run on 10 queries completes unattended and writes a summary.
  • 80% or more email recall on the pilot list; 95% precision on valid status, measured by bounces in the first 300 sends.
  • Every exported contact has source URL, jurisdiction, and lawful basis.
  • Adding an email to the suppression list removes it from the next export.

Decisions the session must make

  1. Postgres hosting: Docker on the VPS or Neon. Lean: Docker, nightly backups to R2.
  2. ORM: Drizzle or Prisma. Lean: Drizzle.
  3. HTML storage: Postgres or object storage. Lean: object storage keyed by URL hash, trimmed text in Postgres.
  4. Which verifier API, by price per credit and catch-all handling.
  5. Which sequencer, by API quality for pushing leads and receiving webhooks.
  6. How the pilot list becomes the acceptance test.
  7. Discovery query templates and the first ten cities.
  8. The exact extraction schema and classification prompt, with ten hand-labelled examples.
  9. Hook prompt and a review flow; a CLI printing tomorrow's hooks is enough.
  10. Secrets management and backups on the VPS.
