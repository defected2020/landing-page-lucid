Lucid Code Labs · Internal · Written 15 September 2026 · For George's review

Mission Dock, always on.

A small always-on hub on the Hetzner box that hosts Claude and Codex agents, mirrors Mission Dock's missions and workspaces, talks to Trello and Habitica with the same keys, and serves a web app on the Lucid domain. The notch, the phone and any browser then steer the same agents and the same task lists, and a piece of work can move between the server and the Mac in either direction.

Hermes traffic Mission Dock link Cloud services First-party Claude features, no code needed
1 hubNode + Postgres on the box you already pay for
2 runtimesClaude Code and Codex, both in tmux
5 phasesabout 8 weeks, useful after week 2
≈ €15–25a month, all in, on the existing Max plan

How to read this. Sections 01 to 10 describe what exists, what gets built and in what order. Section 11 lists the eight decisions only you can make, with a recommendation for each. Section 14 is the kick-off checklist for the first four days. Everything in 01 was checked on the live server, the Mission Dock tree and the Lucid repo on 15 September 2026.

What the viability report already settled

docs/CLOUD_VIABILITY.md (11 Sep) looked at three routes: port the app to Linux (a rewrite; WhatsApp and the voice loop can never move), keep an always-on Mac (works, needs a Mac mini), or use Claude's own cloud (agents only, invisible to Mission Dock). It recommended the Mac mini.

This plan is the fourth route it left open: not a port, a hub. The Mac stays the home of the notch, the panes, WhatsApp, voice and the journal vault. The server hosts the things that gain from being always on: agents, the task mirror, the website. Mission Dock becomes a client of the hub, which the report itself called "a natural later extension of RemoteAPI".

The Lucid site is Next.js on Vercel, deployed from main on every push. Its admin area serves repo-shipped documents; this page is one of them.

02

The shape of it

Seven rules that keep this small. Every design choice below follows from one of them.

  1. Trello and Habitica are already in the cloud.There is nothing to "sync" for them. Mission Dock and the hub both talk to their APIs with the same credentials. The website edits boards directly; the Mac sees the edit through the polling it already does, plus a nudge over the link so it is immediate.
  2. Sync only what Mission Dock owns.Missions, workspace definitions, agent runs and their events, pending decisions, announcements, a settings snapshot. The journal vault and Django's memory stay on the Mac until a later phase.
  3. Every entity has one owner; the other side mirrors.An agent run belongs to the machine that hosts its terminal. Missions are shared with last-writer-wins and the identity rules MissionStore already enforces. Events are append-only, so they merge trivially.
  4. The Mac never opens an inbound port.Mission Dock dials out to the hub over TLS with a device token. The hub relays website commands to the Mac through that connection. This is the phone remote's "never port-forward" rule, kept.
  5. One protocol.The hub speaks the phone remote's contract (/api/state, /api/events, /api/decision and friends) with one added field, origin, on every agent row. The PWA you already have works against the hub on day one.
  6. Humans approve the edge.The AGENTS.md rule holds on the server: agents can move a mission to ready-for-review, never to completed, archived or deleted. Permission prompts use the same held-hook mechanism as the notch.
  7. Fail toward the terminal.If the hub is down, server agents keep running in tmux and are reachable over SSH and Remote Control. If the Mac is off, the website still runs server agents and edits Trello and Habitica. Nothing here is a single point of failure for work that is already in flight.
03

Architecture

Six components. Three are new code, two are ports of Swift you have, one is configuration.

new · TypeScript

Hermes hub

One systemd service on the box, Node 22 with type stripping (no build step, like maps-scraper), Postgres 16.

  • Hook receiver: the loopback line protocol, held PermissionRequest connections, decisions table.
  • State document built every second, diffed, pushed over SSE, agents tagged origin: "hub" or "mac".
  • Link server for Mission Dock (WebSocket): sync batches, relay, presence.
  • Trello, Habitica, GitHub and ntfy clients.
  • Serves the web app and the API behind Caddy.
new · on the box

Agent runtime

One tmux session per run, named hermes-<runId>, as the hermes user.

  • Spawns claude with the same flags the Mac uses, plus AGENTDOCK_RUN_ID for correlation.
  • Spawns codex the same way; codex exec for headless jobs.
  • Pane text via tmux capture-pane (400 lines, the phone's cap); briefs and answers via send-keys.
  • Per-mission git worktrees under /srv/hermes/work.
new · web

Mission Dock Web

The PWA, grown. Served by Hermes at dock.lucidcodelabs.com, linked from the Lucid admin.

  • Phase 1: agents, decisions, briefs, pane view, spawn (what the PWA does today).
  • Phase 3: Trello lists and boards, Habitica, missions, announcements, Django chat, "Mac online" presence.
  • Passkey login, httpOnly cookies, push via ntfy (Web Push later).
Swift · Mission Dock

Hub client in the Mac app

The one place the app changes shape. Details in section 07.

  • HubClient: outbound WebSocket, reconnect, device token in the Keychain.
  • HubSync: the outbox and cursors from DATA_MODEL.md §5.
  • Hub agents in LIVE AGENTS with a hub badge; their prompts answered from the notch.
  • Remote panes, "Assign to Hermes", Django's run_remote tool, handoff actions.
ported · TypeScript

Integrations

Straight ports of Swift you have, with tests carried across.

  • TrelloService and HabiticaService methods the tools use.
  • HabiticaTrelloSync: complete one side, the other follows.
  • RemotePush: edge-triggered ntfy with the same rate limits.
  • The hook → status mapping and the decision JSON, pinned by the same test cases.
configuration

Box preparation

Once, by script, the way setup-server.sh did it for the scraper.

  • Resize, swap, hermes user, /etc/hermes.env.

Two flows, end to end

A server agent asks permission

  1. claude in tmux fires the PermissionRequest hook.The shim connects to Hermes on loopback and holds the socket, exactly as on the Mac.
  2. Hermes stores a decision row and marks the run needs-you.The next state tick goes out over SSE; ntfy pings the phone; the Mac's link gets the same row.
  3. You answer from anywhere.Website tap, notch button, or the Claude app if that session is under Remote Control. First answer wins; the others see it disappear.
  4. Hermes writes the decision JSON down the held socket.The shim echoes it to stdout, Claude Code applies it, the run goes back to working.

You move a Trello card from the phone

  1. The website calls Hermes.POST /api/tasks/trello/move with the card and the list.
  2. Hermes calls Trello with your key and token.The same pair the Mac keeps in its Keychain, copied once into /etc/hermes.env.
  3. Hermes nudges the Mac if it is online.A trello.changed relay message; Mission Dock posts its own trelloDidChange and the Tasks panel refreshes.
  4. If the card is a mission, Hermes updates the mission too.Same rules as the Mac: moving to Done is a human act, so it completes the mission; agents cannot do this step.

05

Agents on the box

Claude Code and Codex run as real interactive sessions in tmux. That keeps Remote Control, hooks and your existing pane tooling all working unchanged.

Why tmux and not a headless SDK loop

A claude TUI in tmux behaves exactly like a pane on the Mac: the same hooks fire, the same PermissionRequest hold works, --resume works, and the Claude iPhone app can attach to it with Remote Control. The Agent SDK (@anthropic-ai/claude-agent-sdk) is the right tool for the hub's own Django later, where a JSON plan is wanted rather than a terminal; it is the wrong tool for sessions a human wants to sit in.

Remote Control is the zero-code head start

Before a line of Hermes exists, claude remote-control running in a tmux session on the box gives you: start a session on the server from the Claude app, steer it, answer its permission prompts, attach files, see subagents, all on the subscription. The docs state it works on a remote machine inside tmux or screen. What it does not give you is Mission Dock visibility, Trello and Habitica, missions, Codex, handoff, or the Lucid-domain web app. Those are what Hermes adds. Spike 2 in the checklist is exactly this test.

ModeCommandUse
Server modeclaude remote-controlServes on-demand sessions the Claude app can create, default capacity 32. Runs in the foreground, so in tmux. Gives up after about ten minutes of outage.
One sessionclaude --rc or /rc inside a sessionExposes that one session to the app; retries indefinitely. This is what a Hermes-spawned run turns on.
ConstraintsSubscription login only, direct access to api.anthropic.com (no GLM base URL on those sessions), the telemetry-off environment variables must stay unset, and the project must have been trusted once by running claude in it.

Runtime details

  • Correlation. Hermes sets AGENTDOCK_RUN_ID when it spawns, the shim folds it into every hook event, and the run id becomes the row key. Sessions started by hand in tmux still show up, keyed by session id, the way iTerm sessions do on the Mac.
  • Versions. DISABLE_AUTOUPDATER=1, and the server's claude is kept within one minor of the Mac's (2.1.272 today), because the hook and decision JSON shapes track the CLI. A single hermes update-claude script upgrades and runs the contract tests.
  • Selectors. Since CLI 2.1.26x the PermissionRequest hook also fires for AskUserQuestion, so most prompts arrive as decisions. For the remaining scraped selectors, the hub answers with tmux send-keys using the option index, the same index the phone already sends.
  • Isolation. Everything runs as hermes, never root. One worktree per mission under /srv/hermes/work/<mission>; --add-dir only inside /srv/hermes; the scraper's user and database are untouched.
  • Repos. A bare clone per repo under /srv/hermes/repos, fetched through a GitHub deploy key registered with the same script that did it for maps-scraper. Start with maps-scraper, landing-page-lucid and the web projects. Mission Dock itself stays Mac-only: nothing on Linux can swift build it.
  • Recurring chores (nightly tests, dependency bumps) do not need the hub at all: Claude routines run them on Anthropic's cloud on a schedule or from a webhook. They stay invisible to Mission Dock, which is fine for chores.

The website

Mission Dock Web is the phone remote with a real address, a real login and the task lists added. It is a remote, not a second Mission Dock.

Where it lives

Served by Hermes at dock.lucidcodelabs.com, behind Caddy, with a link in the Lucid admin sidebar next to Documents and Files. The alternative, building it inside the Next.js admin on Vercel, was considered and set aside: server-sent events do not survive serverless function timeouts, and the admin's password login would need a second bridge to the hub's device tokens. One origin means the API, the SSE stream and the page share cookies and need no CORS. The Lucid site keeps what it is good at: documents, files and this plan.

08

Handing work over

A run moves as a packet: the branch carries the code, the transcript carries the conversation, the brief carries the intent.

The packet

Repo name, branch (hermes/<mission-slug>), base commit, Claude session id, the transcript JSONL, a brief the agent wrote about where it is, what is next and what is open, and any pending decisions. Codex runs carry the brief only, since their history lives in Codex's own store.

Server → Mac

  1. You choose "Bring back here" on the row.From the notch, the website or the pane menu.
  2. Hermes asks the agent for a handoff brief, then to commit and push.A fixed prompt, or a /handoff command shipped in each repo's .claude/commands. The session ends; the Stop hook confirms.
  3. Hermes stores the packet and offers it over the link.If the Mac is off, the offer waits and shows on the Home tab.
  4. Mission Dock fetches and checks out the branch.In the workspace's repo, or in a worktree if that repo is busy in another pane.
  5. The conversation resumes.The transcript is copied to ~/.claude/projects/<encoded cwd>/<id>.jsonl and a pane spawns claude --resume <id>; the docs say --resume also accepts a transcript path and searches every project on the machine. If it fails to open, the pane spawns plain claude with the brief as its first prompt through spawnBriefedAgent.
  6. The row changes origin.The hub run is marked handed off; events from both halves stay under one mission.

Mac → server

The mirror image. Mission Dock already knows every pane's transcript_path from the hooks, pushes the branch, uploads the transcript, and Hermes starts claude --resume in a fresh tmux session under the repo's worktree. The Mac pane closes only after the server confirms the session is up.

Rules. The source session ends before the target starts, so there is never two agents on one branch. A handoff is a mission event with the human as actor. Spike 3 in the checklist verifies the transcript path trick on both machines before any of this is built; if it does not hold, the brief path is the design and the transcript is kept as an attachment for reading.

09

Security

The hub can answer permission prompts and start agents that hold tools. It is treated like the phone remote, with a public address.

  • Surface. Ports 22, 80 and 443 only. Caddy terminates TLS; Hermes listens on loopback. fail2ban on SSH. Optionally Tailscale on the box and the Mac, after which SSH and the link can leave the public internet and 22 closes.
  • Login. Passkey with a recovery code; rate-limited; every failed attempt logged. Device tokens are hashed at rest and shown once.
  • Secrets. /etc/hermes.env, mode 0600, owned by hermes: the OAuth token or API key, Trello key and token, Habitica id and token, the ntfy topic, the GitHub deploy key path. Nothing secret in Postgres or logs. The Mac keeps its Keychain; the copy is made once by hand.
  • Untrusted text. Card titles and descriptions are a prompt-injection surface (AGENTS.md). Briefs wrap them as delimited data, on the server as on the Mac, and the website renders everything with textContent.
  • Authority. Agents cannot complete, archive, delete or merge. The hub enforces it in the API, not only in the UI. Every website action lands in audit with the actor.
  • Blast radius. Agents run as hermes in their own worktrees; the scraper's data and user are separate; no sudo anywhere in the runtime.
  • Policy. Subscription use on a personal server is a grey area the viability report already flagged. Single user, same account, no resale. The API-key fallback is a one-line change in the env file if that ever changes.
